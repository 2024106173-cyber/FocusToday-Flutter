# 오늘한눈 중간프로젝트 발표 원고

발표자: 전시우 / 목표 시간: **6분** / 질의: **2분**

## 본문 1장 · 주제 소개 (약 30초)

안녕하세요. 저는 전시우입니다. 제 중간프로젝트는 할 일 관리 앱의 UX/UI를 개선하는 '오늘한눈'입니다. 기존 앱의 공개 리뷰를 분석하고, 한 가지 문제를 중심으로 사용자 여정, 원인 분석, 화면 기획, Flutter 프로토타입까지 연결했습니다. 완전한 상용 서비스를 만드는 것이 아니라, 설계 근거가 실제 화면에 어떻게 반영되는지 보여드리겠습니다.

## 본문 2장 · 기존 앱과 리뷰 (약 55초)

비교 대상으로 Google Tasks를 선택했습니다. Google Play의 공개 리뷰에서 두 가지 비슷한 요구를 발견했습니다. 2026년 5월 20일 리뷰는 섹션별 색상 구분을 요청했고, 8월 27일 리뷰는 모바일에서 목록별로 색상을 구분하기 어렵다고 말했습니다. 반면 9월 29일 리뷰에서는 미완료 작업을 다시 알려주는 경험을 장점으로 평가했습니다. 제가 우선 해결하기로 한 문제는 여러 목록의 작업을 모바일에서 빠르게 구분하기 어렵다는 점입니다. 다만 리뷰 세 건이 전체 사용자를 대표하지 않으므로, 이것을 확정된 사실이 아니라 UX 개선 가설로 다루었습니다.

## 본문 3장 · 앱 목표와 페르소나 (약 45초)

가상의 사용자 김서연은 수업, 팀 과제, 생활 일정을 한 앱에 기록하는 대학생입니다. 이동 중에 잠깐 스마트폰을 확인할 때 여러 종류의 작업을 빠르게 파악하고 싶어 합니다. 오늘한눈의 목표는 사용자가 어떤 카테고리의 작업을 먼저 해야 하는지 쉽게 알아보는 것입니다. 카테고리를 색상과 글자로 동시에 표시하고, 중요도를 텍스트와 정렬 순서로 보여 주는 화면을 계획했습니다. 색에만 의존하지 않는 것도 중요한 원칙입니다.

## 본문 4장 · 사용자 여정과 핵심 문제 (약 50초)

사용자 여정은 진입, 탐색, 판단, 행동, 재확인의 다섯 단계입니다. 가장 불편할 것으로 가정한 시점은 두 번째 탐색 단계입니다. 학생이 학교와 개인 할 일을 한 번에 훑을 때 목록 맥락을 구분하기 어려울 수 있기 때문입니다. 피쉬본에서는 화면 구조, 시각 언어, 사용 환경과 접근성을 원인 후보로 보았습니다. 5 Why를 통해 항목 레벨에서 카테고리 의미가 일관되게 전달되는지가 핵심이라는 가설에 도달했습니다. 그래서 이번 프로젝트에서는 색상과 텍스트 라벨을 함께 제공하는 문제 하나에 우선순위를 두었습니다.

## 본문 5장 · v2 화면 기획 (약 55초)

화면은 오늘, 전체, 예정, 완료함을 중심으로 구성했습니다. 오늘 화면에는 진행률과 작업 목록을 배치하고, 카드마다 학교, 생활, 개인 카테고리를 색과 문자로 구분했습니다. 중요도는 높음, 보통, 낮음으로 직접 표시합니다. 빠른 추가는 BottomSheet를 사용해 제목과 핵심 정보를 한 번에 입력하게 만들었습니다. 작업을 완료한 경우에도 완료함 탭에서 다시 확인하거나 되돌릴 수 있습니다. 화면 ID는 P01부터 P10까지 정했고, 상세 기능과 상태 화면은 부록 B5에 정리했습니다.

## 본문 6장 · Flutter UI 데모 (약 75초)

이제 구현 화면을 보여드리겠습니다. 앱을 실행하면 로컬 json-server에서 GET 요청으로 작업을 불러옵니다. 먼저 오늘 화면에서는 진행률, 카테고리 라벨, 중요도 표시를 확인할 수 있습니다. 빠른 추가 버튼을 누르고 새 작업을 입력한 다음 카테고리와 우선순위를 선택합니다. 이때 데이터는 현재 화면에만 추가되며 서버에 영구 저장되지 않습니다. 다음으로 작업을 완료하고 완료함 탭에서 다시 찾는 동작을 확인할 수 있습니다. 마지막으로 상단 메뉴에서 로딩, 오류, 빈 상태 화면을 보여드리겠습니다. Navigator와 BottomSheet를 활용했고, 상태는 간단한 setState로 변경했습니다.

## 본문 7장 · AI 반론과 결론 (약 50초)

설계를 검토하면서 AI의 반론을 받았습니다. 첫째, 색만 사용하면 접근성 문제가 생길 수 있다는 지적에 따라 텍스트 라벨을 추가했습니다. 둘째, AI 자동 우선순위 추천은 근거가 불명확하고 과제 범위를 넘기 때문에 제외했습니다. 셋째, 완료 작업을 바로 숨기는 설계는 복구가 어렵다는 반론에 따라 완료함과 실행 취소를 보완했습니다. 가장 중요한 점은 개선 효과를 아직 사용자 테스트로 증명하지 않았다는 것입니다. 이번 결과는 공개 리뷰에 근거한 UI 가설과 작동 가능한 화면이며, 이후 실제 학생에게 찾기 속도와 오류를 측정해 검증할 계획입니다. 감사합니다.

## 2분 질의응답 예상

**Q1. 왜 Google Tasks를 선택했나요?**  
A. 제가 선택한 '할 일 관리 앱' 분야의 대표적인 기존 서비스이며, 스토어에 시각 구분을 요청한 공개 리뷰가 있어 개선 가설을 세울 수 있었습니다.

**Q2. 색만 넣는 것이 충분한가요?**  
A. 충분하지 않습니다. 색과 카테고리 글자를 함께 표시했고, 실제 개선 여부는 사용자 테스트가 필요합니다.

**Q3. 왜 실제 추가/수정 API를 만들지 않았나요?**  
A. 수업의 평가 범위가 UX/UI 기획과 작동하는 UI 시연이라서 GET으로 자료를 읽고 변경 사항은 setState로 보여주었습니다. 영구 저장은 의도적으로 제외했습니다.

**Q4. AI가 전부 만들었다면 셀프 논증은 무엇인가요?**  
A. AI의 반론을 근거로 제 설계 판단을 다시 검토하는 과정입니다. 발표 전 본인이 최종 선택과 반론 근거를 확인해야 합니다.

**Q5. 실제 사용자가 더 좋아하나요?**  
A. 아직 검증하지 못했습니다. 리뷰를 기반으로 가설을 정리했고, 후속 테스트 지표를 제안한 단계입니다.
